## 🐛 El bug real, por fin diagnosticado

Durante meses el cierre con Ctrl+W fallaba de forma intermitente mostrando un residuo `9;9u` en la terminal. Instrumentando las tres capas (kernel → X server → kitty) con una pulsación **física real**, la causa quedó clara:

> En VMware con teclado español, la pulsación física de **Ctrl+W llega al sistema como Super+W**, no como Ctrl+W.

Por eso:

- El residuo `9;9u` era la cola exacta de `ESC[119;9u` — la codificación kitty de *super+w* (si fuera Ctrl real sería `119;5u`).
- Todas las capas previas escuchaban solo Ctrl: kitty mapeaba `ctrl+w`, sxhkd tenía `ctrl + w` y los binds de bash cubrían variantes de Ctrl. **Nadie escuchaba Super.**

## ✅ La solución: todas las capas aceptan ambas teclas

| Capa | Antes | Ahora |
|---|---|---|
| **kitty** | `map ctrl+w` | `map ctrl+w` **+ `map super+w`** → diálogo directo dentro del terminal |
| **sxhkd** | `ctrl + w` | `ctrl + w` **+ `super + w`** → diálogo global en cualquier ventana |
| **bash** | 5 binds CSI-u de Ctrl | **8 binds**: Ctrl (`119;5u`, `87;5u`, `23;5u`, `119;7u`) **y Super** (`119;9u`, `87;9u`, `119;13u`, `9;9u`) |

**Verificado con la pulsación física del usuario**: diálogo Si/No aparece, y al responder *Si* la ventana se cierra. El log de diagnóstico `/tmp/whitehatso-close.log` confirma cada disparo.

> 💡 Si tu sesión lleva tiempo abierta: las ventanas de kitty ya abiertas no tienen los binds nuevos de bash — ejecuta `exec bash` dentro o abre una ventana nueva. sxhkd se recarga solo en el próximo login (`pkill -USR1 -x sxhkd` si quieres forzarlo).
